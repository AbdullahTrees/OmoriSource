# Test-port memory recovery (2026-10-26)

## Root cause investigation

The device was left with `/tmp/omori-r4` (extracted runtime/package, about 137 MiB)
and `/tmp/omori-r4.zip` (about 50 MiB). muOS mounts `/tmp` as tmpfs. These staging
files consumed 187 MiB of a 973 MiB, swapless device even with no game running.
The initial idle MemAvailable was only 595 MiB.

The previous handover blamed the expansion from four to ten performance modules,
but had not controlled for this environmental memory pressure. The test install
already had menu prewarming disabled by renaming its file to `.js.off`.

Restoring the four-module October 24 set alone still hit the 60 MiB watchdog at
58 MiB during the menus sequence. Moving the two exact staging paths into the
port backup on SD raised idle MemAvailable from 580 to 766 MiB. Repeating the
same r3 menus sequence then completed with minimum logged available memory of
220 MiB, final RSS 662 MiB, and no watchdog. The staging archive hash was
unchanged. No caches, saves, game files, system libraries or native runtime were
modified for this comparison.

| --- | --- | --- | ---: |
| October 24 four-module set | 187 MiB | watchdog killed | 58 MiB (watchdog sample) |
| Same set | moved to SD | all phases completed | 220 MiB (10-second samples) |
| Latest patches, prewarm opt-in guard | absent | all phases completed | 160 MiB (10-second samples) |

## Preventing recurrence

- Stage release archives and extracted runtimes on disk, never RAM-backed `/tmp`.
  Check the actual mount type and available memory before attributing a crash to
  code. Preserve suspicious files outside tmpfs before retesting.
- The device harness now records MemAvailable, Shmem, swap and `/tmp` filesystem
  use before each variant. It does not automatically delete anything.
- Menu prewarming now requires `OMORI_PERF_MENU_PREWARM=1`. Packaging a wildcard
  of perf modules must not activate this experiment. Earlier device evidence
  recorded a 20.6-second first-map stall; this remains a separate regression.
  `OMORI_PERF_DISABLE=menuPrewarm` takes precedence over the opt-in.

## Validation

All nine existing perf test files and the sprite-culling checks passed locally.
The revised prewarm test passed 36 checks both locally and on the device's Node,
covering no-opt-in behavior, explicit opt-in and disable-list precedence.
The two controlled r3 logs are preserved in the private handover evidence folder
`evidence/recovery-20261026`, sessions `20261026-011012-menus` and
`20261026-011315-menus`. The newer set passed session `20261026-011629-menus`,
with every scene-transition check true, no watchdog, final heap/RSS 180/668 MiB.
Screenshots confirmed that menu and Options text/controls were visible.

Map 92 before opening the menu measured 33.8 FPS for r3 versus 53.2 FPS for the
newer patches. Both had approximately 60 FPS steady menus/Options. After menus,
the map measured 31.3 versus 34.7 FPS; this is a short sequence comparison, not
a claim that all gameplay stays at 53 FPS. The retained culling and slippery
cache counters were active in the newer run.

The final 20-cycle menu/Options soak (`20261026-011932-soak`) completed all
20 opens and returns with no failed transitions, no forced GC, no feature
toggling, and no watchdog. Across 80 in-game samples, minimum MemAvailable was
99 MiB; the 10-second launcher samples bottomed at 106 MiB. After-close samples
in cycles 11-19 stayed at 106-109 MiB. Native canvas memory stabilized at 42 MiB,
and final heap/RSS was 169/738 MiB (maximum sampled RSS 748 MiB). This is bounded
recovery evidence, not a multi-hour or all-save-files stability guarantee.

The normal shortcut was left unchanged (both device paths and its backup hash
identically). The latest game-side patches remain installed with the opt-in
prewarm guard; runtime addon hash remains `e2c6b8f4aa143fc789ba01f815f09ffaf11b23947ed8f6c8fec9e1da6d0864b0`.
No game process remained at the final check, idle MemAvailable was 763 MiB, and
`/tmp` used 56 KiB. The test shortcut still starts normally at the title; the
harness driver is supplied only through per-run environment variables.

A broad rollback was therefore not retained. The local recovery branch keeps
the later fixes and performance gains, while all original device content and
the staging archive remain backed up on SD. The public release was not rebuilt
or published, and its separate install was not otherwise changed.
